# Workbench Usage

A **workbench** is a multi-repo devcontainer for your own repositories: one
container that holds several clones under `repos/`, with Dev Fortress's
toolchain, persisted logins and shell history, and optional components such as
Claude Code. You describe it in one small TOML file, and `ft` generates the
rest.

> [!NOTE]
> "Workbench" is the multi-repo devcontainer you create for your own repos.
> "Workspace" is the `ft workspace` profile and runtime used to develop Dev
> Fortress itself; see the [container usage guide](container-usage.md).

## Layout

```text
~/.config/dev-container-fortress/workbenches/
  mybench.toml                      # yours: edit it, keep it in dotfiles

~/workbenches/mybench/              # generated by ft; safe to delete and re-render
  .devcontainer/devcontainer.json
  mybench.code-workspace
  repos/
    first-repo/
    second-repo/
```

The TOML file is the only thing you own. The folder holds generated files and
clones, so a new machine needs only the TOML file and three commands.

## Create a Workbench

You need Docker, Git, and `ft` on the host. For the devcontainer CLI terminal
mode you also need the `devcontainer` CLI (`brew install devcontainer`).

```bash
ft workbench init mybench \
  --profile ubuntu-full \
  --options claude-code \
  --repo https://github.com/you/first-repo.git \
  --repo https://github.com/you/second-repo.git
ft workbench clone mybench
```

`init` writes `~/.config/dev-container-fortress/workbenches/mybench.toml` and
renders `~/workbenches/mybench/`. `clone` clones each repo that is missing from
`repos/`, on the host with your host Git credentials.

Then open it in one of two ways:

- **VS Code:** `code ~/workbenches/mybench`, then "Dev Containers: Reopen in
  Container". Open `mybench.code-workspace` inside the container to see each
  repo as its own folder.
- **Terminal mode:** `devcontainer up --workspace-folder ~/workbenches/mybench`,
  then `devcontainer exec --workspace-folder ~/workbenches/mybench zsh -l`.

The repos are bind-mounted from the host, so edits are shared both ways.

> [!TIP]
> On a new machine, restore the TOML file (for example from your dotfiles) and
> run `ft workbench render mybench && ft workbench clone mybench`.

## The Workbench File

```toml
name = "mybench"
# directory = "~/workbenches/mybench"
profile = "ubuntu-full"
# local_build = "~/src/dev-container-fortress"
trust = "full"
options = ["claude-code"]
mounts = []
extensions = []
repos = [
  "https://github.com/you/first-repo.git",
  "https://github.com/you/second-repo.git",
]
```

| Key | Meaning |
| --- | --- |
| `name` | Names the workspace file and the Docker volumes (`dev-fortress-wb-<name>-*`). Lowercase letters, digits, and `-`. |
| `directory` | Where the folder is rendered. Defaults to `~/workbenches/<name>`; a relative path is relative to the TOML file. |
| `profile` | An `ft workspace` profile from [`profiles.toml`](../ft/workspaces/profiles.toml). It sets the image, its tool layers, and the persisted mounts. `ubuntu-base` and `ubuntu-full` have published images. |
| `local_build` | Build the image from a Dev Fortress checkout instead of pulling the published one. A relative path is relative to the workbench folder, so `repos/dev-container-fortress` builds from a clone. |
| `trust` | `full`, the only level today. A locked-down `sealed` level is planned in [`M5d`](milestones/M5d-sealed-agent-workbench.md). |
| `options` | Optional components installed at container start, such as `claude-code`. Host-only options, such as the tmux profiles, are rejected. |
| `mounts` | Persisted mounts to add to the profile's, such as `aws` or `gnupg`. |
| `extensions` | VS Code extensions to add to the defaults. |
| `repos` | Git URLs to clone into `repos/`; each lands in the folder `git clone` would pick. |

After editing the file, run `ft workbench render mybench` (or
`ft workbench render` for every workbench), then rebuild or reopen the
container. `ft workbench list` shows what you have.

> [!IMPORTANT]
> Do not edit the generated `devcontainer.json` or `.code-workspace`; the next
> render overwrites them. `ft workbench render mybench --check` reports drift.

## What Persists

Each workbench gets named volumes for shell state (`zoxide`, `atuin`,
`~/.local/state`), the Homebrew prefix, the `gh` and `glab` logins, Claude Code
when selected, and the profile's other mounts. They survive "Rebuild
Container", `devcontainer up --remove-existing-container`, and moving the
folder, because they are named after the workbench rather than the folder.
Remove them with:

```bash
docker volume rm $(docker volume ls -q --filter name=dev-fortress-wb-mybench-)
```

Inside the container, log in once per workbench:

```zsh
ft identity --login github     # or gitlab
cd repos/first-repo && ft identity --local
```

## Building the Image Locally

Set `local_build` to work on the Dev Fortress image itself, for example to try
an image change before it is published:

```toml
local_build = "repos/dev-container-fortress"
```

Run `ft workbench clone` first so the checkout exists, then render. The local
build turns on the profile's tool layers and OS release, and forwards the same
`DEV_CONTAINER_FORTRESS_*` build variables as the repository's own
devcontainers.

## Caveats

> [!WARNING]
> A `full` workbench protects your host filesystem, not your accounts. Logins
> you make inside it, and any credentials you mount, are fully usable by
> anything running there, including an agent. See "Agents in a Full
> Workbench" in the [M5c milestone](milestones/M5c-composable-container-workspaces.md).

- The repos are bind-mounted, so Git hooks written into `repos/*/.git` from
  inside the container run on the host the next time host-side Git touches
  that repo.
- VS Code windows attached to an already-running container skip the
  extensions and settings in `devcontainer.json`.
