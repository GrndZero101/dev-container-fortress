# Workbench Usage

A **workbench** is a multi-repo devcontainer for your own repositories: one
container that holds several clones under `repos/`, with Dev Fortress's
toolchain, persisted logins and shell history, and optional components such as
Claude Code. You describe it in one small TOML file, and `ft` generates the
rest.

## How It Fits

Dev Fortress aims to get you to a working development machine quickly, and to
let you rebuild or reshape it just as quickly. Two layers do that:

| Layer | What it is | Built by | What you keep |
| --- | --- | --- | --- |
| Workstation | The host: Docker, `shell-config`, the Homebrew toolchain, and `ft` | The [quickstart](../quickstart.md) one-liner | Your option selection, `~/.config/dev-container-fortress/options.toml` |
| Workbench | A container per set of repos, on the same toolchain | `ft workbench` | One TOML file per workbench, under `~/.config/dev-container-fortress/workbenches/` |

Everything else is generated or cloned from those files, so you can delete a
workbench folder, add a repo, swap the profile, or move to a new machine, and
get back to the same place with a few commands. Keep
`~/.config/dev-container-fortress/` in your dotfiles and the whole setup
travels with you.

> [!NOTE]
> "Workbench" is the multi-repo devcontainer you create for your own repos.
> "Workspace" is the `ft workspace` daily-driver container that mounts your
> Dev Fortress checkout; see the [workspace usage guide](workspace-usage.md).

## Layout

```text
~/.config/dev-container-fortress/workbenches/
  mybench.toml                      # yours: edit it, keep it in dotfiles

~/workbenches/mybench/              # generated by ft; safe to delete and re-render
  .devcontainer/devcontainer.json
  mybench.code-workspace
  repos/
    first-repo/
    second-repo/
```

The TOML file is the only thing you own. The folder holds generated files and
clones, so a new machine needs only the TOML file and three commands.

## :clipboard: Before You Start

1. **A Dev Fortress workstation.** Run the [quickstart](../quickstart.md) in its
   default `host` mode, then open a new terminal so your user picks up the
   `docker` group. That installs everything a workbench needs on the host:
   `ft`, Docker, Git, `shell-config`, and the Homebrew toolchain, including the
   `devcontainer` CLI.
2. **VS Code with the Dev Containers extension**, if you want the VS Code path.
   Dev Fortress does not install desktop apps. Terminal mode needs only the
   `devcontainer` CLI.

A thin host from `--mode workspace` has Docker but no Homebrew, so it lacks
the `devcontainer` CLI. Re-run the quickstart without `--mode workspace` to
turn it into a full workstation; nothing is removed.

> [!WARNING]
> **WSL2:** use VS Code on Windows with the WSL extension, and set
> `dev.containers.executeInWSL` as described in the
> [devcontainer usage guide](devcontainer-usage.md), or VS Code starts Docker
> Desktop instead of using the distro's Docker CE.

## :rocket: Create a Workbench

```bash
ft workbench init mybench \
  --profile ubuntu-full \
  --options claude-code \
  --repo https://github.com/you/first-repo.git \
  --repo https://github.com/you/second-repo.git
ft workbench clone mybench
```

`init` writes `~/.config/dev-container-fortress/workbenches/mybench.toml` and
renders `~/workbenches/mybench/`. `clone` clones each repo that is missing from
`repos/`, on the host with your host Git credentials.

Then open it in one of two ways:

- **VS Code:** `code ~/workbenches/mybench`, then "Dev Containers: Reopen in
  Container". Open `mybench.code-workspace` inside the container to see each
  repo as its own folder.
- **Terminal mode:** `devcontainer up --workspace-folder ~/workbenches/mybench`,
  then `devcontainer exec --workspace-folder ~/workbenches/mybench zsh -l`.

The repos are bind-mounted from the host, so edits are shared both ways.

## The Workbench File

```toml
name = "mybench"
# directory = "~/workbenches/mybench"
profile = "ubuntu-full"
# local_build = "~/src/dev-container-fortress"
trust = "full"
options = ["claude-code"]
mounts = []
extensions = []
repos = [
  "https://github.com/you/first-repo.git",
  "https://github.com/you/second-repo.git",
]
```

| Key | Meaning |
| --- | --- |
| `name` | Names the workspace file and the Docker volumes (`dev-fortress-wb-<name>-*`). Lowercase letters, digits, and `-`. |
| `directory` | Where the folder is rendered. Defaults to `~/workbenches/<name>`; a relative path is relative to the TOML file. |
| `profile` | An `ft workspace` profile from [`profiles.toml`](../../ft/workspaces/profiles.toml). It sets the image, its tool layers, and the persisted mounts. `ubuntu-base` and `ubuntu-full` have published images. |
| `local_build` | Build the image from a Dev Fortress checkout instead of pulling the published one. A relative path is relative to the workbench folder, so `repos/dev-container-fortress` builds from a clone. |
| `trust` | `full`, the only level today. A locked-down `sealed` level is planned in [`M5d`](../project/milestones/M5d-sealed-agent-workbench.md). |
| `options` | Optional components installed at container start, such as `claude-code`. Host-only options, such as the tmux profiles, are rejected. |
| `mounts` | Persisted mounts to add to the profile's, such as `aws` or `gnupg`. |
| `extensions` | VS Code extensions to add to the defaults. |
| `repos` | Git URLs to clone into `repos/`; each lands in the folder `git clone` would pick. |

After editing the file, run `ft workbench render mybench` (or
`ft workbench render` for every workbench), then rebuild or reopen the
container. `ft workbench list` shows what you have.

> [!IMPORTANT]
> Do not edit the generated `devcontainer.json` or `.code-workspace`; the next
> render overwrites them. `ft workbench render mybench --check` reports drift,
> and names any filesystem guardrail a hand edit breaks (see Caveats).

## What Persists

Each workbench gets named volumes for shell state (`zoxide`, `atuin`,
`~/.local/state`), the Homebrew prefix, the `gh` and `glab` logins, Claude Code
when selected, and the profile's other mounts. They survive "Rebuild
Container", `devcontainer up --remove-existing-container`, and moving the
folder, because they are named after the workbench rather than the folder.
Remove them with:

```bash
docker volume rm $(docker volume ls -q --filter name=dev-fortress-wb-mybench-)
```

Inside the container, log in once per workbench:

```zsh
ft identity --login github     # or gitlab
cd repos/first-repo && ft identity --local
```

## Building the Image Locally

Set `local_build` to work on the Dev Fortress image itself, for example to try
an image change before it is published:

```toml
local_build = "repos/dev-container-fortress"
```

Run `ft workbench clone` first so the checkout exists, then render. The local
build turns on the profile's tool layers and OS release, and forwards the same
`DEV_CONTAINER_FORTRESS_*` build variables as the repository's own
devcontainers.

## :arrows_counterclockwise: Rebuild and Recompose

| To | Do |
| --- | --- |
| Add or drop a repo, option, or mount | Edit the TOML file, run `ft workbench render mybench` and `ft workbench clone mybench`, then rebuild the container |
| Start the folder fresh | Delete `~/workbenches/mybench`, then `render` and `clone` again; logins and history stay in the volumes |
| Start the container state fresh | Remove the `dev-fortress-wb-mybench-*` volumes (see What Persists) |
| Set up a new machine | Run the quickstart, restore `~/.config/dev-container-fortress/` from your dotfiles, then `ft workbench render && ft workbench clone` for every workbench at once |

Repos come back from their remotes, so push before you delete a folder or a
machine.

## Caveats

> [!WARNING]
> A `full` workbench protects your host filesystem, not your accounts. Logins
> you make inside it, and any credentials you mount, are fully usable by
> anything running there, including an agent.

| Protected by the container | Not protected |
| --- | --- |
| The host OS, packages, and services | Anything the mounted or forwarded credentials reach: forges, cloud accounts, and SSH hosts |
| The host home directory, dotfiles, and host-side tools | The bind-mounted `repos/`: an agent can delete uncommitted work there |
| Other host checkouts outside `repos/` | The network: the LAN, host services, and cloud metadata are as reachable as from the host |
| The Windows side of a WSL2 host | Prompt injection: content an agent reads can steer it toward anything in this column |

Running an agent with permission prompts bypassed in a `full` workbench has
the same account exposure as running it on the host. A locked-down `sealed`
level is planned in
[`M5d`](../project/milestones/M5d-sealed-agent-workbench.md).

The filesystem side is enforced. `ft workbench render` refuses to write, and
`ft workbench render --check` fails on, a `devcontainer.json` that would let
the container reach past `repos/`:

- a container-runtime socket (`docker.sock`, `podman.sock`, `containerd.sock`),
  which amounts to root on the host
- a bind mount of the host home directory, `/`, or a Windows drive such as
  `/mnt/c`
- `--privileged`, added capabilities (`--cap-add`, `capAdd`), or
  `--network host`

Other sockets, such as an SSH agent, and bind mounts below the home directory
stay allowed. The one such bind mount a workbench carries is the
[host browser bridge](devcontainer-usage.md#host-browser-bridge) folder, so
logins in terminal mode open the host browser; the bridge opens only `http`
and `https` URLs.

- The repos are bind-mounted, so Git hooks written into `repos/*/.git` from
  inside the container run on the host the next time host-side Git touches
  that repo.
- VS Code windows attached to an already-running container skip the
  extensions and settings in `devcontainer.json`.
